# Verifying a release

You do not have to trust a wallet download. This guide goes from quick
integrity checks to building the app yourself, in increasing order of effort
and assurance. The threat model behind these steps is in
[`SECURITY.md`](../SECURITY.md).

## 1. Verify the download checksum

Every release attaches a `SHA256SUMS-<platform>.txt` generated by the CI job
that built the artifacts. After downloading, compare:

```bash
# macOS
shasum -a 256 "LDK Wallet_0.4.10_aarch64.dmg"
# Linux
sha256sum "LDK Wallet_0.4.10_amd64.AppImage"
```

```powershell
# Windows
Get-FileHash -Algorithm SHA256 ".\LDK Wallet_0.4.10_x64-setup.exe"
```

against the matching line in the sums file (`SHA256SUMS-windows-x86_64.txt` for the installer), or use the helper:

```bash
scripts/verify-release.sh checksums "LDK Wallet_0.4.10_aarch64.dmg" SHA256SUMS-macos-aarch64.txt
```

Unsigned Windows installers trip SmartScreen ("Windows protected your PC"). That is expected. After the checksum matches, choose More info, then Run anyway.

This proves your download was not corrupted or swapped after CI built it. It
does not prove the source code is honest — for that, keep reading.

## 2. Verify build provenance (attestations)

Every artifact digest is attested by GitHub's build provenance service at
build time, cryptographically linking it to the exact commit and workflow run
that produced it. With the [GitHub CLI](https://cli.github.com/):

```bash
gh attestation verify "LDK Wallet_0.4.10_aarch64.dmg" --repo LitecoinDevKit/ldk-wallet
```

A successful verification shows the source commit and the workflow file that
built the artifact. This defeats an attacker who can replace release assets
but cannot forge GitHub's signing infrastructure.

### Minisign signature (offline verification)

When a release includes `SHA256SUMS-<platform>.txt.minisig`, the checksums
file is additionally signed with the project's minisign key, so verification
does not depend on GitHub at all:

```bash
minisign -Vm SHA256SUMS-macos-aarch64.txt -P <project public key>
```

The public key is published in the repository README once signing is active;
cross-check it from more than one channel (repo, release notes) before
trusting it.

## 3. Check the macOS signature (signed releases)

CI signs and notarizes macOS artifacts automatically when Apple Developer
secrets are configured (see [`NOTARIZATION.md`](NOTARIZATION.md)). Draft release
notes state whether that run was signed or unsigned.

**Signed / notarized** builds:

```bash
codesign -dv --verbose=4 "/Applications/LDK Wallet.app"   # identity + team ID
spctl -a -vv "/Applications/LDK Wallet.app"               # Gatekeeper / notarization
```

Expect `Developer ID Application` and `accepted` from `spctl`.

**Unsigned** builds fail these checks. That is expected when repository secrets
are absent. Clear quarantine once, then prefer building from source or waiting
for a signed release:

```bash
xattr -cr "/Applications/LDK Wallet.app"
```

## 4. Cross-check the dependency pins

The wallet's key handling and MWEB cryptography live in the fork repositories,
which are rev-pinned in the Cargo manifests and `Cargo.lock`. Inspect the pins
at the release tag:

```bash
git show v0.2.1:crates/wallet-core/Cargo.toml | grep 'rev ='
git show v0.2.1:Cargo.toml | grep 'rev ='
```

CI builds only from those pins (`cargo --locked`), so the manifests at the tag
are authoritative for what shipped.

## 5. Verify address derivation independently

Paranoid-mode check that the wallet derives the addresses your seed should
produce — run on an offline machine with a throwaway seed first:

```bash
cargo run -p wallet-cli -- derive --network mainnet --count 5
# seed is read from stdin, so it stays out of shell history
```

Compare the derived addresses against another implementation (Electrum-LTC,
litecoind, or a hardware wallet with the same seed).

## 6. Check your local secret storage

After creating a wallet:

```bash
DATA_DIR="$HOME/Library/Application Support/com.indigonakamoto.ltc-wallet" # macOS
# DATA_DIR="$HOME/.local/share/com.indigonakamoto.ltc-wallet"             # Linux
# DATA_DIR="$env:APPDATA\com.indigonakamoto.ltc-wallet"                    # Windows (PowerShell)

ls -l "$DATA_DIR"
```

On macOS and Linux, expect `wallet.mnemonic.enc` with mode `-rw-------` (0600), and **no**
plaintext `wallet.mnemonic` file (legacy plaintext files are migrated to
encrypted storage on first unlock, then deleted). On Windows the same filenames
live under `%APPDATA%\com.indigonakamoto.ltc-wallet`; that profile is private to
the user, and there is no Unix mode to check. MWEB data is sealed too:
after the first sync you should see `mweb_coins.enc`, `mweb_sync.enc`,
`mweb_receive_index.enc` and `mweb_history.enc` instead of the older
plaintext `mweb.sqlite` / `mweb_*.json` files.

## 7. Build from source

The strongest check: build the exact pinned source and compare with the
released artifacts.

```bash
scripts/verify-release.sh source-build v0.2.1
```

This clones the repo at the tag plus the three pinned siblings, builds, and
prints SHA-256 hashes of the produced bundles.

**Honest caveat:** builds are not yet bit-for-bit reproducible. Container
formats (`.dmg`, `.AppImage`, the Windows `.exe`) embed timestamps, and the binary depends on the
exact Rust toolchain (CI uses the version pinned in
`.github/workflows/release.yml`). Matching hashes are strong evidence; a
mismatch means "investigate" (start by comparing the app binary inside the
bundle), not necessarily "compromised". Full reproducibility is tracked as
future work in `docs/AUDIT_NOTES.md`.

## What you cannot verify (yet)

- No third-party audit has been performed. `docs/AUDIT_NOTES.md` holds the
  internal review findings and the intended scope for an external audit.
- macOS artifacts remain unsigned on any release built without Apple
  credentials in CI ([`NOTARIZATION.md`](NOTARIZATION.md)).
- Bit-for-bit reproducible builds (see caveat above).
